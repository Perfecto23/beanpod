# 得到 AI 录音卡（GetSeed）蓝牙协议笔记

豆仓接入得到 AI 录音卡（GetSeed，型号 GSC10）时用到的协议。

## 出处

**这份协议不是豆仓逆向出来的。** 全部协议事实来自
[Shawn-TKD/getseed-ble-protocol](https://github.com/Shawn-TKD/getseed-ble-protocol)
（MIT 许可，Copyright (c) 2026 Shawn-TKD；参考的版本是提交 `c42918a`，2026-10-17）。
原作者用实机抓包、官方 App 分析和固件分析整理出了这份协议，并用 Python 工具在实机上验证过。

豆仓按那份文档用 Swift 从零实现（`Sources/BeanKit/GetSeed.swift`、`Shared/CardClient.swift`、`Shared/CardSync.swift`），
没有拷贝原项目的代码。下面只摘录豆仓用到的部分，细节和证据请看原项目。

**豆仓还没有在实机上测过录音卡。** 下表「豆仓的状态」一栏说明了哪些只是按文档实现、还没核对。

## 认设备

| 项 | 值 | 豆仓的状态 |
|---|---|---|
| 广播名 | `Get-XXXXXX`（后 6 位是序列号尾号） | 按文档实现 |
| 厂商 ID | `0x544A`（广播里是小端 `4A 54`） | 按文档实现，作为名字之外的第二个判断依据 |
| 服务 UUID | 广播里没有 | — |
| 配对、绑定 | 都不需要；同一时间只能被一台设备连着 | 按文档实现 |

## 通道

只用「控制」这一条通道，录音的列表、下载、删除都走它，而且是**明文**：

| 服务 | 写 | 通知 |
|---|---|---|
| `00009100-0000-1000-8000-57616c6b697a` | `…9101` | `…9102` |

另外两条通道豆仓不用：`00009000-…`（加密的短命令，不承载录音）、`66666666-…`（芯片方案商的默认命令通道）。

豆仓还会尝试读蓝牙标准的电量服务（`180F` / `2A19`）。原项目在 Android 系统日志里看到卡上挂着标准 Battery 服务，
但没有直接读过电量值，所以**这一项要等实机确认**；读不到就不显示电量。

## 帧

```
FC FC FC FC | cmd (u16 LE) | len (u16 LE) | body (len 字节) | crc32 (u32 LE)
```

`crc32` 是 zlib 的 CRC‑32，算的是它前面所有字节。豆仓发出的帧带 CRC（单元测试里用 Python `zlib.crc32` 的结果核对过）；
收到的帧不校验 CRC（原项目的工具也不校验），按帧头和长度切。

## 用到的命令

| cmd | 方向 | body | 说明 |
|---|---|---|---|
| `0x0146` | → | 14 个 ASCII 字符 `YYYYMMDDHHMMSS` | 对时，回 `01`。卡里的文件名按卡上的时钟起，所以一连上先对时 |
| `0x0042` | → | 空 | 存储信息，回 12 字节：4 字节 + **剩余空间 KB（u32 LE）** + 4 字节 |
| `0x0050` | → | 空 | 状态查询（官方 App 要列表前会先发） |
| `0x0043` | → | `01 00 00 00 05 00 00 00` | 文件列表，回一段文字：`序号,文件名,YYYY-MM-DD HH:MM:SS,字节数;`，分号隔开。列表为空是正常的 |
| `0x0145` | → | `00 00 00 00` + 文件名 | 下载一条 |
| `0x0245` | ← | u32 | 文件大小；文件不存在时为 0 |
| `0x0345` | ← | 偏移 u32 + 最多 472 字节 | 数据块，连续推，不用逐块应答。**偏移是这一块的结束位置** |
| `0x0445` | ← | u32 | 传完了 |
| `0x0545` | ← | 1 字节 | 出错；`5A` = 文件不存在 |
| `0x0044` | → | 文件名 | **永久删除**这一条，回 `01` 成功 / `00` 失败 |

录音文件是完整的 Ogg Opus（16 kHz 单声道，卡上的 FFmpeg 编的），不用解密，也不用自己封装。
豆仓原样存成 `.ogg`，再按第一个 Opus 包的 TOC 字节算出帧长、用系统解码器转成 16 kHz WAV 给播放和转写用。
蓝牙下载约 25 KB/s（原项目实测）。

### 豆仓自己的推断（还没核对）

- **列表分页**：`0x0043` 的 body 推测是「第 1 页、每页 5 条」。原项目只发过第 1 页。
  豆仓的做法是：一次正好回满 5 条，就再要下一页（第 2、3…页）；回来的全是已经有的、或者不满 5 条，就算列完。
  如果卡其实一次就回全部，这样做最多多问一次，不会出错。
- **时长**：列表里没有时长。文件名是开始录的时刻，第三列在原项目的例子里正好比文件名晚出录音时长，
  豆仓就用两个时间相减来估时长；下载后以解码出来的实际时长为准。

## 豆仓刻意不做的

- **不发 `0x0041`**。官方 App 一连上就发这条，它会永久删除卡里「已经传过」的录音（「同步完卡就空了」就是它）。豆仓的代码里根本没有这条命令。
- **不会自动删除**卡里的录音。只有你在设备页对某一条点「从录音卡删除」并确认后，才发 `0x0044` 删这一条。
- **不能远程开始、停止录音**。固件里有这个功能，但原项目还没找到对应的命令，所以只能在卡上按键录。
- **不做 Wi‑Fi 快传**。原项目只做了静态分析，没有在实机上验证。

## 已知的风险

- 固件升级可能改协议。原项目分析的是固件 0.1.8。
- 录音卡的录音是明文、连接不需要任何鉴权：附近任何蓝牙设备都能连上读走录音。这是设备本身的设计，豆仓改变不了；
  不用的时候把卡放在身边、注意别被陌生设备连上。
